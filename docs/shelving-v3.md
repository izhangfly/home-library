# 上架算法 v3 —— 整屋布局规划

> 起因：v2 只会「某层溢出了 → 把最小的一组挪走」。这是个局部补丁，
> 回答不了用户真正问的问题：
>
> * 每类有多少书事先根本不知道，**分区必须能自己涨大、缩小、搬家**
> * 距离要**分层级**算：同层之间、同柜不同层之间、柜与柜之间、房间与房间之间
> * 学科近的要放得近
> * 儿童书要放低，不常用的放高
> * 而且要**可靠** —— 不能今天一个结果明天另一个

## 1. 问题到底是什么

一开始容易把它想成装箱（bin packing），那是 NP 难的，只能启发式，
"可靠"就无从谈起。但书架问题有一个装箱没有的结构：

> **书有全序。** 索书号（中图法分类号 + 著者号）把所有书排成一条线。

图书馆之所以能用一套规则管上千万册书，靠的就是这个。有了全序，
"哪些书放哪一格"就不是任意分组，而是**把一条有序序列切成连续段**
—— 这是多项式可解的动态规划，不是 NP 难问题。

这一个建模决定，是整个 v3 可靠性的来源。

### 参考的现成理论

| 问题 | 对应到这里 |
| --- | --- |
| **有序序列的连续切分**（LeetCode 1105 "Filling Bookcase Shelves" 那一类） | 书按索书号排好，每个书柜/每层拿走连续的一段。DP 可求全局最优 |
| **list-labeling / 文件维护问题**（Itai–Konheim–Rodeh；Bender 等） | 插入一本书要挪动邻居。结论是**空隙要摊匀，不能囤在末尾**；均摊 O(log²n) 次移动 |
| **图书馆书库管理经验值** | 上架装填率 70–75%，留出的空间不是浪费，是日常上架的必需品 |
| **二次分配问题 QAP**（把类目摆到货位上，最小化加权距离） | 一般情况 NP 难。但**要求顺序单调之后就退化成上面的 DP** —— 顺序单调本身就保证了学科近的挨着 |
| **仓储 slotting / golden zone** | 齐腰到齐肩是黄金取货区，高频货放那儿。这里换成"常翻的书"和"孩子够得着" |

## 2. 三层分解

```
第 0 层 货架带（shelf tape）：把所有层排成一条人走过去会依次看到的线
第 1 层 柜级 DP：把有序书列切成连续段，每段给一个书柜
第 2 层 柜内 DP：一个柜子内部，把它那一段再切给各层，这里管人体工学
第 3 层 在线插入：来一本书时的增量算法，不重排全局
```

为什么在柜级和柜内分两层，而不是一个大 DP 直接切到层？

* **可找到性**发生在柜级：你先走到那个柜子，再扫。柜与柜之间顺序错了，
 人就找不着；柜**内部**上下差一层，一眼扫过去就看见了。
 正因如此，柜内允许**整体翻转**（从上往下读 或 从下往上读），两个方向
 各跑一遍 DP 取便宜的那个。这一个自由度是"童书在下、冷门在上"的前提：
 童书排在常用书前面时，若强行从上往下读，童书就被顶到最高层去了。
* **人体工学**只在柜内有意义：同一个柜子里哪一层齐腰、哪一层要踮脚。
* 分开之后柜级的代价函数可以很便宜（前缀和 O(1) 算），
 柜内的规模又极小（≤10 层 × ≤几百本），两边都跑得动。

真实图书馆就是这么干的：架与架之间严格按分类号顺序，一架之内你自己扫。

## 3. 货架带的顺序

* 房间之间：从平面图上离入口最近的房间开始，贪心最近邻走一圈（确定性的）
* 房间内：书柜同样按最近邻排
* 书柜内：层由下到上编号，但**带的顺序取从上到下** —— 和图书馆一架书
 从左上读到右下的习惯一致

顺序只依赖户型图坐标，不依赖数据库里的插入时间，所以是稳定的：
同样的房子永远得到同样的带。

## 4. 距离：四个尺度

```
d(a, b) =
 同一层 0
 同柜不同层 |Δ离地高| × w_vert （伸手，便宜）
 同房间不同柜 平面欧氏距离 + 换柜固定代价 （转身走两步）
 不同房间 房间质心距离 + 换房间固定代价 （要走出去）
```

`w_vert = 0.3`：竖直方向 1 米比水平方向 1 米便宜得多，因为你不用挪脚。
换柜/换房间的固定代价（1.5m / 6m 当量）表达的是"注意力的成本"——
你得重新定位、重新扫一遍。

**学科距离**用中图法前缀：`clcCloseness(a,b) = 公共前缀长度 / 较长者长度`，
同一个大类至少 0.25。前缀深度天然就是学科树上的距离，不用另外造一个矩阵。

两者在代价函数里通过**切口代价**耦合：

```
切口代价(第 k 本和第 k+1 本被分到不同柜子) = w_cut × closeness(k, k+1) × d(柜j, 柜j+1)
```

意思是：**要断就断在学科的缝上**。两本书关系越近、被分开后物理距离越远，
代价越高。这一项就是"学科近的放得近"的全部实现 —— 顺序单调保证了
近的本来就挨着，DP 只需要决定在哪儿断开。

## 5. 代价函数

单位统一成"毫米当量"，权重才好解释。

### 柜级（第 1 层）

```
cost(柜 j 装第 i..k 本) =
 w_fill × usable × (装填率 − 0.75)² × (超了 ? 26 : 0.3) 装填偏离目标
 + 装不下 ? ∞ : 0
 + w_move × |{这段里当前不在柜 j 的书}| 惯性
boundary(j, j+1, k) = w_cut × closeness(k,k+1) × d(柜j, 柜j+1)
```

二次惩罚是从 list-labeling 学来的：线性惩罚会把所有空隙推到最后一个柜子，
二次惩罚才会摊匀。摊匀的意义是**下次插入时挪动的书最少**。

**但它必须不对称**，这是性质测试逼出来的（见 §10）。对称的二次惩罚下，
把一层塞到 100%（偏离目标 0.25）比空着一层（偏离 0.75）便宜九倍，于是算法
把够得着的几层塞满、把够不着的空着。第一版跑出来的装填分布是
`0 0 78 98 99 | 98 97 98 23 22 | …` —— 一半的层没有一毫米余量。
每层都塞满意味着以后插进一本书就要推挤一整排，等于把日常上架变成了搬家。
图书馆的 70–75% 规矩，本质说的就是"宁可空着，别塞满"。
改成超额罚 26 倍、不足罚 0.3 倍之后，同一份数据变成
`18 13 79 83 82 | 49 47 80 82 82 | …`，没有任何一层超过 92%。

### 柜内（第 2 层）

```
cost(层 s 装这段里的第 p..q 本) =
 w_fill × usable × (装填率 − 0.75)²
 + 有书比层高高 ? ∞ : 0
 + Σ 人体工学代价(书, 层)
 + w_move × |{当前不在层 s 的书}|
```

人体工学代价：

```
ergo(书, 层) =
 w_reach × (1 − reachScore(层, 这本书的主要读者))
 + w_zone × 错位惩罚
```

* 读者从分类号推：`I28*`（儿童文学）、`G62*`（小学教育）等 → 孩子（140cm）；
 其余 → 成人（按家里最矮的 160cm 算，保证谁都够得着）
* 错位惩罚：**常翻的书放到够不着的高处**罚得重；
 **不常翻的书占了黄金区**罚一点点（浪费了好位置）
* "常翻/不常翻"没有阅读记录可依，就用能拿到的证据：标签（常翻/待读）、
 工具书类目（Z 类、辞书）算常用，期刊、多卷套书算低频。
 证据不足就算"普通"，**不瞎猜**。

错位惩罚是一张货位偏好矩阵，而不是单向的"高处扣分"：

| | 低层 | 黄金区 | 顶层 |
| --- | --- | --- | --- |
| 常翻 | 0.4 | **0** | 1.0 |
| 普通 | 0.15 | 0.2 | 0.15 |
| 冷门 | 0.7 | 1.0 | **0** |

只罚"高处"是不够的：低层本来就没有罚分，冷门书会全堆到最下面，而不是像
用户要的那样上到顶层去。必须显式表达"冷门书**应该**在高处"。

#### 两个诚实的边界

1. **使用频次只能在类目粒度上生效。** 索书号顺序不能打乱，所以同一个类里
 按著者号排的那几十本，不可能把其中某几本单独提到低层。这是"可找到性优先"
 的代价，测试 F 明确按这个口径断言。
2. **架子紧张时，"常翻的好拿"优先于"冷门的上顶层"。** 一个柜子往往只有一层
 算得上"顶层"，冷门书塞不下就得往下走。测试分成两档：架子紧的那档断言
 *常翻书拿到黄金区*（取用质量 1.00 vs 0.20），有余量的那档才断言
 *冷门书被推到更高处*。

## 6. 惯性：一个旋钮同时解决"理想布局"和"最少搬动"

用户的硬约束是：**不可能把书全抽出来重摆，只能一架一架来。**

传统做法是先算理想布局、再算差分，然后想办法削减差分 —— 两步之间没有
统一的目标，结果不可控。

v3 的做法是把"搬动"直接写进代价函数：

```
w_move = 0 → 从零开始的理想布局
w_move = ∞ → 一本都不动
w_move 适中 → 只在明显划算的地方动
```

于是同一个 DP，调一个旋钮就得到从"大扫除"到"只补一格"的连续谱。
而且它自动满足用户提的"优先挪小的那一组"：小组的惯性代价本来就低。

默认 `w_move = 350`（毫米当量）—— 大约等于"为了搬一本书，收益至少要
相当于腾出 35cm 的合理空间"，实测下来只有真的溢出时才会触发。

## 7. 在线插入（第 3 层）—— `lib/insert.ts`

来一本新书时**不跑全局 DP**：

1. 沿货架带找到它按索书号该去的那一层
2. 那一层放得下 → 直接插入，结束（绝大多数情况）
3. 放不下 → **推挤**：把该层最后一本推到下一层，级联下去，直到遇到有空隙的层。
 这正是 list-labeling 的做法，也是人在书架前实际会做的动作
4. 级联超过预算（默认 8 本）→ 不再自作主张，出一份预览，交给用户确认

第 3 步是"分区自己涨大缩小"的实现：分区边界随着推挤自然移动，
没有人需要去维护一张"哪个类目占哪几层"的表。

### 带的方向必须照着架上现在的样子读

第一版把柜内方向写死成"从上往下"（图书馆惯例），上线立刻出了错答案：
用户的书是从最底层往上摆的（第 1 层 I247 → 第 4 层 N4），
于是一本 I516 被算成该放进装着 N4 的最上层。

`planLayout` 本来就允许每个柜子整体翻转（§2），柜内方向从来就不是固定的。
所以 `shelfTape()` 现在按**现有藏书的索书号**判方向：两个方向各走一遍，
数逆序，少的那个就是这个柜子实际的读法。

### 落在两层之间时挑哪一层

一本书正好排在「上一层最后一本」和「这一层第一本」之间时，接在上一层末尾、
或插在这一层开头，两种都不破坏顺序。挑法：

1. 只有一层放得下 → 就是它
2. 都放得下 → **跟同类走**（比 `clcCloseness`）
3. 还并列 → 挑余量大的

第 2 条不能省。只比余量的话，两层余量常常只差几毫米，谁大谁小纯属偶然，
同一个类目就会被随机切成两半。

## 8. 什么时候整段搬家

推挤解决不了的情况：一整个类目长到装不下所在的柜子。这时才谈搬家，
判据是柜级 DP 的结果 —— 如果重新切分之后总代价的下降超过了惯性代价，
就出搬家建议，并且给出理由：

> 「I247 中国当代小说 已经涨到 2.1m，客厅大书柜装不下。
> 建议把 K5 世界史（0.4m，12 本）整段挪到书房矮柜第 2 层 ——
> 挪它比挪小说少搬 28 本，而且 K 类和书房现有的 K2 是邻居。」

## 9. 总容量够 ≠ 切得开

柜级 DP 用的容量是"这个柜子所有层的可用宽度之和"，这是**乐观**的：
书是整本的，不能劈成两半分给两层。总量正好卡在容量上时，柜内 DP 会直接判
不可行，那一柜的书就全丢了（第一版在 5000 本的压力测试里安排数是 0，
1318 本"放不下"，其实是这个 bug）。

所以逐柜落实时带一次修复：装不下就二分回退区间末尾，多出来的顺延给下一个
柜子；比所有层都高的书先摘出来单独报告，免得一本超高书卡死整柜。

## 10. 别把全家卡住 —— 服务端必须切片跑

这段是纯 CPU，而 Node 是单线程：它跑多久，**整个服务就多久不响应任何人**。
一个人点一下「整屋规划」，全家其他人扫码的请求就得排队等着。实测：

| 藏书 | 书柜 | 总耗时 | 其中柜级 DP | 同步跑时别人最长等 |
| --- | --- | --- | --- | --- |
| 2000 | 10 | 485ms | ~95% | **486ms** |
| 5000 | 20 | 1.63s | ~98% | **1.63s** |
| 10000 | 40 | 6.2s | ~98% | 6.2s |

（柜内 DP 在 5000 本时只占 38ms，热点完全在柜级那个三重循环上。）

所以 `planLayout` 的实现体写成了生成器 `planLayoutGen`，两个驱动器共用它：

* `planLayout(...)` —— 同步抽干，测试和脚本用，行为和以前一模一样
* `planLayoutAsync(..., sliceMs = 40)` —— **服务端一律用这个**，
 每片最多占 40ms 就把事件循环还回去

让出的粒度要够细：只在柜子之间让出的话，藏书上千之后单个柜子那一轮就要一百多毫秒，
所以柜内每 256 个状态也让一次。效果（5000 本）：

```
同步 总耗时 1634ms 别人最长等 1634ms
切片 总耗时 1644ms 别人最长等 91ms
```

总耗时基本没变，别人的等待从 1.6 秒降到 90 毫秒。

因为两者共用同一个生成器，算法一个字没改；测试里另有一条（L）断言两种跑法
的搬动数、代价、每本书的落点、放不下和例外清单**完全一致** ——
否则就会变成"测的是一套代码，线上跑的是另一套"。

## 11. 小类合并要说出来

家庭书架上必然有一堆"只有三五本"的类：环境科学、航空、综合工具书。
每类都占不满一层，算法自然会把它们拼在同一层 —— 这是对的，
连续切分本来就会这么切。

问题在于**界面只报 `dominantClass`**：一层上拼了五个小类，屏幕上只显示最大的那个，
另外四类等于凭空消失，人走到架子前才发现"这儿怎么还有别的书"。
用户当初的原话就是：小类合并到一层时要**告诉他合并了什么**。

所以每层现在额外报一份 `classes`（按大类统计，占用宽度降序），
计划级别再挑出「≥2 个大类、且其中有占不满四成的小类」的层作为 `merges`。
两个都挺大的类共用一层是正常的分段边界，不提醒 —— 提醒太多等于没提醒。

## 12. 可靠性怎么保证

`scripts/verify-layout.mts` 里是一组**性质测试**，每次改算法都跑：

| # | 性质 |
| --- | --- |
| 1 | 每本书要么被安排，要么被明确列为"放不下"并给出原因 —— 不许静默丢失 |
| 2 | 没有任何一层超过可用宽度 |
| 3 | 没有任何一本书高过它所在层的净空 |
| 4 | 柜级分段连续且递增（索书号顺序不被打乱） |
| 5 | 儿童读物不会被放到孩子够不着的高度，除非被明确报为例外 |
| 6 | **幂等**：对自己的输出再跑一次，搬动数为 0 |
| 7 | **惯性单调**：w_move 增大，搬动数不增 |
| 8 | 加一本书引起的搬动数有上界（不会雪崩） |
| 9 | **确定性**：同样输入永远同样输出 |
| 10 | 5000 本 × 20 个柜子在 2 秒内跑完（现在 1.6–1.8 秒，靠给柜级 DP 的状态加上界） |

第 6、7、9 条是"可靠"的核心：一个每次跑出不同结果、或者跑两遍还在
继续搬书的算法，无论平均质量多好都不能用。

再加两条是测试跑出来才补上的：

| # | 性质 |
| --- | --- |
| 11 | 没有层被塞到 92% 以上 —— 留得住下次上架的空间 |
| 12 | 人体工学上的妥协一条不藏，全部进 `exceptions` 清单 |

第 12 条的做法是：挤不下的时候算法照样安排，但把每一处"这本童书在最高一层"
都记下来还给界面。**不许静默将就** —— 用户至少要知道那是权衡的结果，
而不是算法没考虑过。

在线插入另有一组（K1–K8）：有空位不动别人、满层插队要推挤而不是另找空层、
推挤后整屋索书号仍然升序且没有层超宽、推不动时老实报 `needs_review`、
带的方向跟着实际摆法走、夹在两层之间时跟同类走、以及确定性。

跑法：`npm run verify:layout`。当前 77 条全过。
