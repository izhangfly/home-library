# 家庭图书管理系统

扫 ISBN 建库 → 自动补元数据 → 打标签 → 按书架容量给上架建议 → 之后搜得到、找得着。

线上：**https://library.example.com**
运维、更新、备份见 [DEPLOY.md](DEPLOY.md)。

---

## 怎么用

1. **先建书架**（设置 → 书架结构，需要管理员密码）。
 每一层要填**宽 / 净空高 / 深**，单位毫米。容量计算全靠这三个数，量准一点后面才准。
2. **扫码加书**（扫码页）。对准书背面条码，自动查元数据、给标签建议、算该放哪一层。
3. **上架**。系统给排好序的建议；拿不准的情况它不替你决定，会让你去书架前看一眼再点。
4. **找书**（书目页）。书名、作者、ISBN 都能搜，中文支持拼音和首字母（`三体` / `santi` / `st`）。

权限刻意做得很浅：**加书、删书、上架都不要密码**（妹妹也要能用），
只有**改书架和层的结构**才要管理员密码，免得容量模型被误改带偏。

## 界面风格

Neobrutalism：暖白底、2px 墨色描边、不带模糊的硬投影、高饱和色块。
token 全在 [`app/globals.css`](app/globals.css) 的 `@theme` 里，组件只用语义类
（`.card` `.btn` `.chip` `.field`），不写死颜色。

- 字体 Inter + JetBrains Mono，字号 13/15/17/21/27/35，间距 4/8/12/16/24/32
- 主色 `#FDC800` 是黄的，**只能当底色配深字，永远不能当白底上的文字色**
- 标签颜色由用户自选，所以文字色是按底色算出来的（[`lib/contrast.ts`](lib/contrast.ts)），
 黄标签自动配墨字、蓝标签自动配白字
- 全部前景/背景配对实测过 WCAG 2.2 AA（≥4.5:1）。
 `--color-text-faint` 因此从 `#7a8595`（3.74:1）压深到 `#6b7684`（4.62:1）——
 手机底栏未选中的导航文字用的就是它

## 关键设计取舍

**容量判断不做"聪明的自动化"。**
书脊厚度是估的（页数 × 系数），估算就有误差。所以只要落进临界区间，
系统一律拒绝自己拍板，把决定权交回给人——你去书架前看一眼，塞得下就点「塞得下」。
"系统说放得下、结果放不下"这种事一次都不该发生。
量过的书可以直接填实测厚度，那本书之后就按实测算。

**AI 简介宁可不写，也不瞎写。**
只有所有数据源都没给简介时才会调 DeepSeek，而且提示词里给死了两种输出：
认识这本书就写 2-3 句，不认识就返回"信息不足"。生成结果存在单独字段、
带独立视觉样式和"AI 生成"角标，永远不会和数据源的真实简介混在一起。

**封面下载到本地。**
外站图床会变、会挂、会防盗链。封面统一经 `/api/cover` 抓一次压成 webp 存本地，
这是要留很多年的家庭书目，不该指望别人的 CDN。

## 索书号（杜威十进分类）

每本书都有一个像图书馆一样的索书号，比如 `891.733 DOS`、`895 余华`：
DDC 类号 + 著者号（拉丁名取姓前三个字母，中文名取前两个字）。
书目页可以按**索书号排序** —— 那就是书架上的物理顺序。

号从哪来，按可信度排：

| 来源 | 说明 | 精度 |
|---|---|---|
| `编目权威` | OpenLibrary 的图书馆编目记录 | 原样保留，可能带小数（891.733） |
| `规则推断` | 本地关键词规则，见 `lib/ddc.ts` | 只到三位 |
| `AI 推断` | DeepSeek，不确定时会说 unsure 而不是硬编 | 只到三位 |
| `手动指定` | 你自己填的 | 随你 |

**为什么推断的号只到三位**：DDC 完整类表是 OCLC 的版权资产，本地没有也不该复刻。
实测 8 本书里只有 1 本能拿到权威号，其余都是推断的。
编一个 `895.1352` 出来只会让你以为它可信 —— 所以推断一律停在纲目级，
并且在界面上用 `编目权威 / 规则 / AI` 角标把可信度标出来。

### 两个踩过的坑（已修）

- **子串匹配没有词边界**：`art` 命中了 Sapiens 主题词里的 `…civilization`，
 把人类简史判成了艺术类 700。现在拉丁词按词边界匹配（并放宽复数），中文才用子串。
- **主题词没落库**：第一版只在入库瞬间用了数据源给的主题词，没存。
 重算 DDC 时只剩标题和简介，罪与罚就被中文简介里的"心理"带成了心理学 150。
 现在 `Book.subjects` 落库，重算时证据还在。

证据还按来源加权：主题词 5 分 > 书名 3 分 > 简介 1 分，总分不到阈值就不给号、交给模型。
**错号比没号更难发现**，所以宁可空着。

## 户型图（DXF）

设置 → 书架结构 → 户型图，上传 DXF 就能把书柜摆到真实平面位置上，扫完书直接告诉你
"去客厅那个柜子的第 3 层，离地 88cm"。

- 解析器在 `lib/dxf.ts`，支持 LINE / LWPOLYLINE / POLYLINE / CIRCLE / ARC / TEXT
- 按 `$INSUNITS` 自动换算成**毫米**，和书架层尺寸同一套单位
- 认不出的实体跳过，不会让整份文件解析失败
- 书柜在图上可以直接拖，坐标即时保存（需要管理员）

已导入的这份：12.75m × 18.28m，28 个图元，原图单位厘米。

## 数据源

| 语言 | 实际用的源 | 备注 |
|---|---|---|
| 中文 | **豆瓣**（`m.douban.com/rexxar` JSON 接口） | 元数据最全：书名/副标题/作者/译者/出版社/页数/定价/简介/封面 |
| 英文 | **Google Books**（需 API key）+ **OpenLibrary** | OpenLibrary 无需登录、无配额 |
| 可选 | 万舟 wanzhou | 填 `WANZHOU_BASE_URL` 即自动接入，不填就跳过 |

几点与原始 spec 不同的地方，都是实测之后调整的：

- **Google Books 匿名调用已经不能用了**：不带 key 时配额被降到 0，一律 429。必须配 API key。
- **没有部署 wanzhou**：它要先把 OpenLibrary 全量 dump 拉下来离线建库，
 服务器只剩 16G 空间，成本远高于收益。代码里留了接口，哪天你自己部署了填个环境变量就能用。
- **没有部署 douban-api-rs**：那个仓库 2022 年就归档了，而它做的事就是转发豆瓣页面。
 既然如此不如直接调豆瓣自己的 JSON 接口——少一个服务、少一层 HTML 解析、结构化程度还更高。
- **pdc.capub.cn 保持纯人工**：按 spec 的要求，不写任何自动登录或绕验证码的代码。
 扫码页放了个链接，需要核对 CIP 数据时手动点过去查，回来手改字段。

实测（5 本真书，中英各半）：**全部 7/7 字段命中，零手动补录**。
随时可以重跑：`npm run smoke:sources`。

### 逐源实测（13 本，8 中 5 英）

`npm run compare:sources` / `npm run compare:covers`：

| 源 | 命中 | 平均字段 | 中文 | 英文 | 可用封面 | 平均封面宽度 |
|---|---|---|---|---|---|---|
| 豆瓣 | 13/13 | 6.9/7 | 8/8 @6.9 | 5/5 @7.0 | **13/13** | **514px** |
| Google Books | 12/13 | 5.1/7 | 8/8 @4.1 | 4/5 @7.0 | **0/13** | 128px |
| OpenLibrary | 11/13 | 5.9/7 | 6/8 @5.8 | 5/5 @6.0 | 9/13 | 292px |

两条由此得出的实现细节：

- **封面字段单独排序**（`FIELD_PRIORITY`）。Google Books 免费接口只返回 128px 缩略图，
 一张都达不到可用标准。如果封面跟着整体优先级走，英文书会存下 128px 的糊图，
 而丢掉豆瓣的 500px 版本。所以封面强制 豆瓣 > OpenLibrary > Google Books。
- **豆瓣是主力，另外两个是保险**。真正撑起覆盖率的是豆瓣；Google Books 和 OpenLibrary
 的价值在于交叉校对（冲突会显示给你选）和"豆瓣哪天挂了不至于全瞎"——
 真挂了的话英文书还有 ~6/7，中文书降到 6/8 命中。

## 条码处理

书背面的条码不都是 ISBN，混着查必然大面积失败：

- `978` / `979`（非 `9790`）开头 → 图书 **ISBN**，正常查
- `977` 开头 → 期刊 **ISSN**，后面常跟 2 位或 5 位附加码（期号）。
 数据源基本不收期刊，直接引导手动录入，不浪费一次联网查询
- `9790` 开头 → 乐谱 **ISMN**，同样走手动

校验位不对会明确提示"可能是识别错了，再扫一次"，而不是拿错号去查然后说"查无此书"。

## 容量模型的已知边界

**书脊宽度**靠页数估算：`页数 × 0.052 + 封面厚度`（平装 3mm / 精装 6mm），
系数在设置页可调。量过的书填 `spineMm` 就直接用实测值，那本书之后不再估算。
估算来源会一路传到界面上（实测 / 页数估算 / 无页数兜底），不会把猜的数字伪装成准的。

**书高和厚度没有任何数据源提供** —— 2026-08 实测：Google Books 抽 8 本
`dimensions` 全是 null，OpenLibrary 的 `physical_dimensions` 取不到，豆瓣压根没这个字段。
所以除非你自己量，`heightMm` 永远是空的。这带来一个设计问题：
如果把"书高未知"当成拦截理由，那**每一本书**上架都会弹确认框，确认框就退化成噪音了。

现在的处理：层的净空高度 ≥ `assumedHeightMm`（默认 240mm，覆盖常见 32 开/16 开）时，
高度判为 `assumed_ok` 直接放行；层比这矮才判 `unknown` 并要求你看一眼。
量过书高的书走精确比较，放不下的层直接从建议里剔除。

**层的 `depthMm` 目前只记录不参与判断** —— 书的进深数据同样拿不到，
而且书卡在深度上的情况远比宽度和高度少见。字段留着，将来有数据了可以直接用。

- **书架地图上拖动书柜调位置**：目前房间坐标要在书架结构页手填。
- **书脊宽度按标签/开本分别调系数**：`tagMmPerPage` 字段和计算逻辑都在，
 但设置页还没做对应的编辑界面，要改得直接写数据库。
- DXF 导入、3D 地图（spec 明确列为本期外）。
